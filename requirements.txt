# docling은 고정한다. 2.118은 레이아웃 모델에 torch.compile을 기본으로 켜는데
# (layout_options.engine_options.compile_model=True), 이 이미지에는 g++가 없어
# 컴파일이 페이지마다 실패·폴백한다 — 51p 문서가 5분 안에 끝나지 않는다. 핀 없이
# 재빌드하면 이 상태가 그대로 배포된다.
#
# g++를 넣으면 쓸 수는 있다. 컴파일 단위는 문서가 아니라 (그래프 + 입력 텐서 모양)
# 이라 프로세스가 오래 살수록 상환된다. 실측:
#   정상상태  잡당 20.8s → 17.7s (-15%, 문서별 8~24%)
#   선불      프로세스당 약 108초. 산출물 21MB가 TORCHINDUCTOR_CACHE_DIR에 남아
#             새 컨테이너도 재사용하면 49초까지 줄지만, 그래프 추적·링크 몫인 약
#             31초는 캐시로도 안 없어진다 → 손익분기 약 10잡
#   메모리    모델만 1.17GB → 컴파일 커널까지 얹으면 1.81GB(+0.34GB).
#             잡 처리 중 peak는 2.88GB로 2.111과 같다
# 워밍업은 4페이지 이상 문서로 해야 한다 — layout_batch_size=4라 1페이지 샘플로
# 데우면 배치 모양이 달라 실문서에서 다시 컴파일된다(실측: 워밍업 뒤 첫 실잡 59.4s).
#
# 그래서 보류한다. 15%를 얻자고 g++·캐시·워밍업 문서 세 부품이 늘고, 이 서비스의
# 알려진 실패 모드인 OOM 여유를 0.3GB 깎는다(peak 3.9GB + 0.3 vs mem_limit 5GB).
# 그 외 2.112~2.118에 PDF 경로 개선은 없다 — 출력이 2.111과 바이트 단위로 같았다.
docling==2.111.0
